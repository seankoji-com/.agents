How the skills work together

You do not need the whole library for every change. This page shows who hands what to whom when you do use several skills. Each skill's own file holds the exact rules.

Start with the outcome

Ask for a result and let the agent pick the skills that help. The dashed arrows are choices the agent makes for the task. They are not a fixed sequence.

Settle the choices that change the build

think asks only the questions whose answers would change the next step, then has a reviewer from another model family confirm nothing important is open. choose-design shows mockups from two model families, or three for a new screen, and you pick before UI work starts. An existing design that already answers the question needs no chooser.

Bring evidence to the review

review-loop repairs and re-reviews until the score target and required checks pass, or stops after two rounds that fail to beat the best score. review supplies the reviewer and the evidence and severity rules. design-loop uses the same stopping rule for UI, with judges who use the real interface.

Finish the endpoint you authorised

ship hands the pull request to babysitter, which owns CI, review threads and the merge. Before it waits on a T3 pull request watch, it fixes conflicts, failing checks and open comments. A merge proves a merge. Deployment and live behaviour need their own check.

Feedback does not have to become code

The coordinator can fix a finding, decline an invalid or out-of-scope request with reasons, or file a minor one as a linked issue. Required approvals and changes-requested reviews still block the merge.

Deliver a backlog through ship

backlog-burn keeps independent fixes running in parallel, refilling capacity on every wake and discovering more issues when the ready queue is empty. It uses ship for delivery, with one parent plan and one final retrospective across the run. Its approval limits still apply.

The main coordinator owns PR delivery and native watches. Coding leads and workers default to the main thread's model and effort unless the owner selects another. Reviewers retain implement's cost-aware selection and cross-lineage eligibility. Leads return reviewed commits; the parent does not implement issue fixes inline. The coordinator records why capacity is unused and continues classification, investigation and owner questions when coding slots are full. Ready independent work starts before blocking questions. A watched PR, one unanswered question or a blocked push does not finish other ready work. Unexamined issues and unasked live approvals still need action. Externally owned work gets an explicit hold, takeover or outside-trigger decision. Awaiting-owner applies only when all remaining work is explicitly held or awaits an actual unanswered question. A required host yield preserves the queue and its next action. A merge closes only issues whose acceptance is satisfied; direct publication needs authorization.

Small models read a card, not a skill

A strong model coordinates. The reviewers and workers it starts can be cheaper models, so they get a short card instead of a 1,500-word skill and its links.

Assigned reviewer

The assigned-reviewer card covers the whole job in about 450 words: stay read-only, check your own model family, gather evidence, rate severity and return one report.

Implementation participant

The implementation-participant card tells a worker to repair what it was given, prove each repair and hand decisions back to its parent.

Measured, not guessed

python3 scripts/check_library.py --stats prints how many words each skill loads on its own, with its folder, and if an agent follows every link.

Keep implementation off the main thread

implement starts one lead in its own T3 worktree. The lead codes, adds workers only for large independent parts, and returns reviewed commits. Your main conversation keeps acceptance, integration and shipping.

Cheapest route that does the job

Model choice aims for the lowest total cost including review, retries and repairs. One evidenced model or effort upgrade is allowed per task. It does not reset scores or counters.

Decisions come back to you

If a product or design decision appears, the lead returns it to the main thread and continues only the work that does not depend on it.

File deferred bugs without holding the merge

Every confirmed bug left unfixed needs a verified issue link before the workflow is complete, including minor ones. raise-issue files them in a background T3 task. Filing does not lower severity or waive a blocker.

Visible progress and a look back

One task list in the parent

ship keeps its plan in T3's plan panel and updates the same list through handoffs and resumes. Without a plan tool it says so and posts a short status list at each phase change.

A retrospective from the logs

The last stage reads the run's activity across the parent and every delegate, including failed attempts. Missing logs are reported as a gap. With posting authority, proposed skill changes go to the operator's own configured repository as issues. Otherwise they remain drafts and the retrospective stays incomplete with an owner question. Proposals do not automatically change the skills.

AI-written text is labelled

github-writing opens issues, pull requests and comments with a byline naming the model that wrote them and the person it wrote for.

T3 permission workarounds

Before starting a helper session, skills read the T3 dispatch preflight. It records two host problems reported on 2 November 2026.

OpenCode, Grok and Muse fall back to asking

Their auto mode can drop to ask and stall unattended work (T3 Code #11458). Skills start them with explicit full access when the parent session allows it. A parent in auto cannot start a full-access child, so skills filter those routes out first.

Codex in full access rejects prompt rules

T3 maps full access to Codex's approvalPolicy: "never", so a command matching a Codex prompt rule fails before it runs (T3 Code #12248, Codex #41068). The agent reports that gate. It does not change your rules or mode.
