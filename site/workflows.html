How skills work together

See who owns each step of a pull request, backlog run or delegated build. Find and install skills.

Deliver a pull request

Use the steps that fit your change.

Settle the choices that change the build

think asks only the questions whose answers would change the next step, then has a separate reviewer confirm nothing important is open. Plans have no model-family restriction. vote takes a framed choice with the options already on the table, sends one packet to its T3 workflow, which puts it to Opus, Sol and Neon, and returns the 2/3 result or the split. choose-design shows mockups from two or three Opus designers, each with a different emphasis; Neon and Sol score every option, and you pick before UI work starts. An existing design that already answers the question needs no chooser.

Bring evidence to the review

review-loop repairs and re-reviews until the score target and required checks pass, or stops after two rounds that fail to beat the best score. A failed run gets one automatic reflect-fix-retry before it reports; the skill keeps the rounds, the stop rule and that single recovery in its run record. Each round renders an inline HTML score line graph showing reviewer trajectories, the dotted target, failure/recovery annotations and hover rationales with component dimensions. review supplies the formal reviewer, the score-chart renderer and the evidence and severity rules.

If two code reviews in a row find different material bugs that come from the same design assumption, the coordinator considers a repair that removes that assumption.

Use hillclimb to improve a workflow, artifact or product against a rubric. Confirm the judges, any lead-judge upgrade for the panel and any recovery alternates before work begins. When the full panel joins, the preapproved lead judge swaps in and they all score the same version. UI judges use the running interface. One report shows the evidence and scores. The skill keeps the rounds, the panel's lowest score, the stop rule and the single recovery in its run record.

If either loop fails, the agent reflects, fixes the cause and runs it once more from the latest candidate. A deadline or spending cap already reached stops that retry. A round cap already reached still allows a setup-only fix, and blocks one that changes the candidate. A second failure comes back to you with both attempts and the best candidate. Revised criteria or judges are recorded and flagged against the original target.

Verify delivery

ship hands the pull request to babysitter, which handles CI, review threads and merge verification. It works through actionable failures before registering a T3 pull request watch. Check deployment and live behaviour separately when the task requires them.

Decide how to handle findings

The coordinator fixes material findings, records reasons for declining invalid or out-of-scope requests, and files eligible deferred bugs as issues. Required approvals and changes-requested reviews still block the merge.

Close the finished thread

settle runs last. It saves durable decisions, raises optional follow-ups as new threads, and removes only what the session created. It leaves the thread open while a pull request or owner question still needs its owner.

Drive open issues and pull requests to zero

backlog-burn handles open issues and pull requests together through the workflows/backlog-burn.ts T3 workflow. Code keeps the item ledger, the 20 slots, the implement and review dispatch, the forge reads and the PR waits. Your thread triages, decides merges and writes the report.

For an organisation, it starts one run per repository with open work, skips active runs and returns links to the threads.

The workflow closes an item only after triage classifies it close and the packet carries that authority. It reads every closure back. A list at its 200-issue or 500-PR cap reports partial coverage instead of a false zero.

A fresh inventory verifies zero open issues and PRs. The report records any items still held, awaiting a decision or actively owned elsewhere, and distinguishes delivered fixes from work closed with evidence.

Short role cards for delegates

The coordinator reads the workflow and gives each worker or reviewer the card for their assignment.

Assigned reviewer

The assigned-reviewer card tells the reviewer to stay read-only, check their model's eligibility and return evidence-backed findings by severity.

Implementation participant

The implementation-participant card tells a worker to repair what it was given, prove each repair and hand decisions back to its parent.

Check how much each role reads

python3 scripts/check_library.py --stats prints how many words each skill loads on its own, with its folder, and if an agent follows every link.

Implement in a separate worktree

implement starts one lead in its own T3 worktree. The lead codes, adds workers only for large independent parts, and returns reviewed commits. Your main conversation keeps acceptance, integration and shipping.

Choose coding and review models

The lead weighs coding cost alongside review, retries and repairs. Code reviewers must come from a different model family from the code authors. The primary checks the full scope, including UI behaviour when it changes. The current routing and companion rules are in reviewer model selection and parallel review.

Decisions come back to you

If a product or design decision appears, the lead returns it to the main thread and continues only the work that does not depend on it.

Track deferred bugs

Every confirmed bug intentionally left unfixed needs a verified issue link before the workflow is complete. raise-issue files those issues in a background T3 task. Required fixes and checks still gate the merge.

Progress reports and the retrospective

Task list and timeline

ship, implement and review-loop show phases in T3's Tasks row when it is available. The main thread records unfinished work, blockers and owner decisions in the handoff.

plan-report makes a timeline from a private ledger. ship, backlog-burn and implement use it at proposal, task completion, final handoff and on request. The final report compares actual build and review work with the original estimates.

Evidence at delivery

Visible changes get a captioned screenshot. The coordinator reports any owner-only steps still open and checks the allowed merge method before each merge. The optional one-round review policy lets the coordinator verify eligible repairs from that review. Later findings and new behaviour still follow the normal review rules. See project settings and the one-round review rules.

A retrospective from the logs

The coordinator compares the results with the plan and checks the logs for consequential events or missing evidence. Durable decisions the run settled go to the project's memory. Any proposed workflow changes go to the configured repository as issues when the operator has authorised posting.

AI-written text is labelled

github-writing adds a byline to AI-written GitHub posts and replies. It names the model that wrote the prose and the operator when verified.

T3 permissions and capacity

Before starting a T3 delegate, the coordinator reads the T3 dispatch preflight. Check that reference for current workarounds. A brief or follow-up that only agents will read follows binaric: the answer first, only what changed for a running delegate that still has its brief, and every fact the reader acts on. The coordinator checks each message: anything a person will also read is written for people.

The coordinator checks LiteLLM's subscription snapshot before choosing a route. Within the allowed models and hard gates, it ranks eligible providers by quota pace score (paceScore), checks current headroom (headroomNow) for long tasks, and treats stale or missing observations as unknown instead of inventing thresholds.

OpenCode, Grok and Muse may fall back to asking

The affected T3 routes can drop from auto to ask. Use explicit full access only when the parent session and host allow it. T3 Code #11458.

Codex in full access rejects prompt rules

T3 maps full access to Codex's approvalPolicy: "never", so a command matching a Codex prompt rule fails before it runs. The agent reports the block. T3 Code #12248 and Codex #41068.
