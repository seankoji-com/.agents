# T3 dispatch and startup

Babysitters do their own repairs, checks and reviews. They must not create
delegates, subagents or additional agent threads, including independent reviewers.
This applies to T3, native tools, other providers and helper CLIs. An explicitly
user-directed dispatcher may create initial babysitter assignments only. The
routing instructions below apply to that dispatcher, not to assigned babysitters.
Repository owners assigned several PRs handle them directly without child agents.

Read the exposed tool contracts before choosing a route. If the user explicitly
requested initial delegated assignments, discover `orchestrator_capabilities`
before dispatch, respecting the host's discovery frequency. List registered
projects and relevant active owners; inspect linked
environments only when needed. Match repository identity, including verified
renames, rather than project titles or folder names.

## Choose a supported route first

- No project or scratch coordinator: inventory and route work, but do not assume
  this grants cross-repository delegation. Worktree creation needs a verified
  repository source. Prefer existing repository coordinators; cloning/registering
  a source does not remove the local delegate's parent-project restriction. If
  the host later exposes isolated cross-project initial dispatch, use that documented
  route rather than creating extra visible threads.
- Same project: an explicitly requested initial babysitter assignment may use
  `delegate_task` with `isolation: "worktree"` where supported. Give independent
  writers separate prepared worktrees. The assigned babysitter cannot delegate.
- Another local project: do not pass its project ID to a local delegate when the
  tool limits delegates to the current project. Prefer an existing coordinator
  bound to that repository, using the host's supported handoff mechanism. Preserve
  its existing ownership and limits; do not start a competing coordinator.
- Linked environment: inspect its project and tool capabilities. Do not request
  remote delegate worktree isolation when that contract supports only the project
  checkout. Find a matching existing coordinator with supported isolation instead.
  Prefer a suitable local route over moving work to another machine merely to
  retry dispatch.

When the user explicitly requests new coordinators, prefer one per repository,
handling its assigned PRs directly, over one top-level thread per PR.
For those top-level threads use `t3_thread_launch`, the matching project/environment,
and `workspaceStrategy` of type `worktree`. Use a verified repository base for a
batch coordinator, or the PR source ref for a single-PR owner, following the exposed
`baseRef`/origin semantics. Each babysitter must verify its assigned PR revision.
Inherit the session provider, model and options;
send them explicitly when remote inheritance is unavailable. Use a stable
`clientRequestId` for retries after an error or lost reply, preventing duplicates.
Do not create shell worktrees, use unisolated shared checkouts for independent
writers, modify project setup settings, or invent unsupported arguments.

Do not infer a request for new top-level threads from "dispatch" or "delegate".
Do not rediscover known routing restrictions by sending the same invalid dispatch
for every PR. If no existing coordinator or supported isolated route is available,
record that routing blocker and continue unaffected work. Do not repeatedly ask
the same thread-creation question or silently create per-PR top-level threads.

A separate clone can avoid dirty source checkouts or worktree contention, but only
when the user authorizes it and the host can bind the worker to it. Use exposed
clone/register/workspace tools where applicable. Registering a clone does not make
cross-project local delegation available. Never tell a child to clone or create
its own worktree to escape binding, or make its checkout in the shell contrary to
host rules. Do not introduce a launcher or second orchestration system.

## Give the owner a complete brief

Include PR URL, repository identity, observed source/base refs and SHAs, explicit
publish target, task scope, dependencies, acceptance checks and current owner
decisions. Require fresh checkout/head/base verification before writing: a prepared
worktree can start from a parent commit or use a different local branch name.
Preserve unrelated changes and other writers' commits.

State the user's standing authority accurately: scoped repair, required checks,
normal commits/pushes, review replies/resolution, protected merge and the existing
automatic deployment effects of that merge. Name known deployment effects and
retain the actual user instruction as evidence when available. Do not add a generic
"no deployment" sentence that contradicts this authority. Separate manual release
steps and new spending/infrastructure need their own authority. Preserve current
explicit draft, release and human-review holds; prior progress text is not new
authority or a new hold. No protection bypass or shared-history rewrite.

Identify the owner type explicitly:

- A delegated repair child must not delegate recursively or watch PRs. Its parent
  dispatcher owns the sole native watch and carries the result through merge.
- A top-level babysitter owns its assigned PR lifecycles and one native watch per PR. The
  dispatcher must not create a duplicate watch or claim child completion wakes
  will cover an independent top-level thread. Report its returned link.

## Confirm startup and recover once

Link the PR to its actual owner thread using host linking rules. Follow launch
with `t3_thread_read` or the supported native wait. Check workspace preparation
and agent-start evidence separately. A launch returning `preparing` proves only
creation; report pending setup honestly. Do not report all workers running from
launch receipts. Use native waits/events rather than shell/API polling.

For setup errors such as `openTerminal`, inspect the failed preparation record
and project setup command before retrying. An empty saved scripts list does not
prove that no setup hook ran. Do not assume checkout success means setup succeeded,
disable a required hook, or repeatedly press Retry without changed evidence.
Try one supported correction, such as the same verified repository in a suitable
local environment. Confirm the failed owner has no active run before replacing
it, use a new request ID for the intentional replacement, and remove stale PR
ownership/watch links. Stop task-owned running delegates with `task_cancel`.
Keep failure evidence and use host cleanup for disposable worktrees.

If that correction fails, report the exact setup stage/error and required unblock
action. Continue other PRs. A setup fix belonging to another repository or host
configuration is separate work, not an excuse to edit that configuration silently.

## Approval rejection and continuation

An automatic approval rejection is binding. Do not retry through another tool,
provider, machine or wording to conceal the same action. If it alleges missing
authority, check the actual user instruction and verified deployment policy.
Present that evidence through the supported approval path when allowed; do not
assert that this skill guarantees host approval. If still rejected, report the
exact action/reason and request the missing authorization. Repair-only work may
continue as an explicitly narrower assignment, but record the unresolved merge
gate and do not present readiness as completion of a merge request.

The dispatcher follows every initial delegate's returned `next`; use completion
wakes rather than status polling. Babysitters perform follow-up reviews and repairs
directly. Mandatory independent review needs an existing reviewer or a separately
user-directed assignment; do not manufacture independence through self-review.
Refresh GitHub after results and before merging. Reconcile the ledger on PR events,
including dependencies after prerequisite merges. An unavailable initial dispatch
route is a concrete blocker, not permission to substitute a provider or drop PRs.
