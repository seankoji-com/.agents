# Audit procedure

1. Freeze work and review choices under the shared selection contract before
   substantive work. Identify the repo/owner scope, history access, profiles and
   finite audit time/repo/execution budgets. The target validation budget is always
   600 seconds; it is separate from audit effort. Do not reduce required repository
   verification to fit it. Retained means every enabled activity in the declared
   pre-merge assurance set, even when branch rules fail to enforce it.
2. Collect cheap source/config/report evidence across the declared scope first.
   Capture `audit PATH --snapshot`; bind normalized inputs to that exact SHA and
   source digest. Read configuration and source as data. Never run a discovered
   command by default. Reuse evidence reference IDs across the twelve findings.
   Compose profiles by consequence, including financial/data plus browser risks
   for a financial web app. Shell tools do not need browsers for uniformity.
3. Inspect critical/changed/bug-prone/flaky/slow groups and a documented seeded
   random remainder. The helper returns a reproducible selection. Record actually
   inspected groups and omissions; inventory triage is not a test-value audit.
   Map success, meaningful rejection and recovery to plausible failure families.
   For every group name consequence, observation boundary, independent oracle,
   distinct environment-specific protection, overlap, setup/execution and upkeep.
4. Collect the complete retained graph, setup/install/build/execution/retry/report
   durations and cross-workflow/repo dependencies. Explicitly record pool workers,
   serialization and matrix batches. Preserve submission-to-verdict, queue/ready
   waits, cold/warm setup, runner class, failed/cancelled/timed-out runs and other
   blockers/overall loop latency. Do not subtract overlapping queue intervals from
   aggregates or add parallel job times. Helpers use a capacity-constrained list
   schedule and nearest-rank percentiles. Unknown ready metadata/dependencies make
   timing uncertain. Every observed and modelled breach remains visible, including
   incident outliers; any exclusion is a separately labelled comparison.
5. Preserve first and eventual outcomes, every attempt and per-test/suite counts.
   Fail-then-pass is inconsistency, not a cause. Classify product/test/infra/unknown;
   every intermittent failure needs open/fixed/owned-exception disposition. Fixed
   requires repair evidence, exceptions need owner/reason/compensating evidence/
   expiry and do not erase the gap. Quarantine remains incomplete. Inspect bounded
   predicate polling, whole reruns, transport retries and application retry-contract
   tests separately. Sleeps, swallowed failures, broad catches, retry-only cleanup
   and larger timeouts need inspection rather than automatic deletion.
6. Coverage needs tool/version, denominator unit, source inventory, generated/
   vendored/exclusion policy, uninstrumented languages/subprocesses and per-file/
   line/branch union identity. Counts reveal execution gaps, not detection quality.
   Record named compatible baseline, instrumentation/environment and exact changed-
   code target-base/merge-base policy/SHA. Missing/incompatible comparison is unknown.
   No universal percentage floor or unit/integration/journey ratio.
7. Sample severe/repeated incidents over 90 days, run attempts over 30 days and up
   to ten other recent fixes. State severity/recurrence rules, source access and
   selection counts. Include user, agent, review and operations reports. Trace prior
   misses and pre-fix failure/fixed success when feasible. If the window since the
   predecessor is longer, disclose the unexamined range. No accessible history means
   unknown, never no escaped bugs. Paginated run/job/attempt errors remain visible.
8. Detection claims need historical/pre-fix or bounded plausible faults, or direct
   inspection for obvious tautologies/dead features. No universal mutation minimum.
   Select named critical decisions/failure families, not easy mutants. Compare a
   cheaper suite against the same corpus/environments; report named detected/lost/
   unknown cases by risk, elapsed and compute. Keep equivalent/build-error/timeout
   cases distinct. Never infer a percentage of future safety or invent 80/20 value.
   Rare catastrophic protection can justify keep. Same covered lines, slowness,
   call counts, snapshots or no historical failures alone do not justify deletion.
9. Supply judgments as `findings` and `groups`, with the actual producing shared
   `selection_context`. Unsupported value uses `assessment_state: needs_evidence`,
   `action: null`, unresolved claim/owner/next experiment. Supported actions name
   retained/lost cases and measured versus estimated savings. Compare runner-minutes,
   capacity and monetary/resource requirements to baseline; more runners are a
   tradeoff and grant no purchasing/capacity authority. Rank actions explicitly,
   never use a weighted total to conceal critical unknowns.
10. Save locally with the deterministic helper. Review all twelve states, identities,
    missing shards, report hashes and completeness. Attempt reporting after ordinary
    setup/test failures; distinguish reporting/upload/cancellation/runner-loss gaps.
    Failure to report cannot turn failed tests green. HTML uses escaped inert text,
    restrictive CSP and HTTPS-only diagnostic links. Native interactive reports are
    separate untrusted attachments; never run PR code in a privileged publisher.
    Sanitize credentials and personal fixtures before ingestion. Inspect actual
    desktop/mobile HTML and docs with T3 preview when available. State unavailable
    interactions rather than claiming provider/fleet compatibility from fixtures.

Only ordinary bulky supporting attachments may expire after 30 days. Compact
sanitized records remain until owner deletion. Mark expired evidence unavailable
on revalidation and old heads superseded in the index. Hashes bind inputs/report/
generator, but do not prove authenticity against someone rewriting the manifest.
A successor compares compatible observations and checks whether recommendations
actually improved latency and protection; adoption and causal claims need evidence.
